# Hermes 底座上的 ABot-AgentOS 导航 Agent 设计清单

本文以 **Hermes 作为 CEE-AgentOS 的通用 Agent/Harness 工程底座**，以
**ABot-AgentOS 作为导航具身化改造的唯一系统设计参考**。Hermes 已有的会话、
模型调用、工具循环、插件和上下文能力直接复用；CEE-AgentOS 只补充 AgentOS
要求的场景条件规划、隔离技能执行、物理结果验证、具身记忆、端云路由和安全控制。

主要参考资料：

- [ABot-AgentOS 官方项目页](https://amap-cvlab.github.io/ABot-AgentOS/)
- [ABot-AgentOS 技术报告](https://arxiv.org/abs/2607.10350)

> 说明：ABot-AgentOS 官方没有声明依赖 Hermes。这里的“Hermes 底座 +
> AgentOS 具身扩展”是 CEE-AgentOS 的工程实现选择，不是对官方依赖关系的描述。

## 1. Hermes 与 AgentOS 的职责边界

| 层级 | 在 CEE-AgentOS 中的定位 | 接口边界 |
| --- | --- | --- |
| **Hermes Core** | **唯一通用 Agent/Harness 底座** | 会话、LLM provider、工具调用循环、插件、上下文管理和通用可观测性 |
| **CEE-AgentOS 扩展** | **按 ABot-AgentOS 设计实现的具身控制平面** | 场景条件规划、Skill Runner、分层验证、具身上下文、证据记忆、端云路由和技能演化 |
| 导航技能 | Hermes 可调用的受限具身工具 | 当前由 OmniNav 生成局部轨迹；以后可替换模型，但不改变 AgentOS 协议 |
| 本体运行时 | 物理执行与安全边界 | Habitat 或 ROS2 负责控制、碰撞保护、看门狗、急停和人工接管 |

因此，CEE-AgentOS 不再自建第二套通用 planner/tool/session 循环。Hermes 是唯一
Agent 入口；AgentOS 能力以 Hermes 插件、导航专用上下文、Skill Runner、Verifier
hook、记忆适配器和本体适配器的形式扩展。物理执行状态仍由确定性的具身运行时维护，
不能由 LLM 对话状态代替。

### AgentOS 主线必须保留的能力

- **任务规划与技能编排**：把开放式用户任务转换为带完成条件的技能图，而不是只生成一串文本 TODO。
- **隔离技能执行**：每次技能调用拥有独立上下文、超时、取消令牌和结果协议，避免局部历史污染主 Agent。
- **分层验证**：区分命令已接收、技能有进展、子目标完成和全局任务完成。
- **统一记忆**：将观测、地点、物体、动作结果和来源证据结构化保存，而不是无限追加对话历史。
- **模型与技能路由**：根据任务、时延、算力和置信度选择端侧模型、云端模型或传统算法。
- **可观测运行时**：为规划、技能、模型、控制和验证使用统一 trace，并能拒绝过期结果。

Hermes 承载 AgentOS 的模型调用、会话和工具编排；CEE-AgentOS 在 Hermes 上增加
确定性技能生命周期、验证、安全控制与具身状态持久化，而不是与 Hermes 平行运行。

## 2. 导航 Agent 与通用 Agent 的区别

| 通用 Agent 的常见假设 | 导航 Agent 的必要要求 |
| --- | --- |
| 工具调用成功或抛出异常就能判断结果 | RPC成功只代表命令被接收，必须通过odom和视觉证据验证是否产生了物理效果 |
| 返回的观测默认是当前状态 | 每张图像、pose、地图、模型结果和控制命令都必须带采集时间、帧号、序列号和新鲜度限制 |
| 文本历史足以充当记忆 | 记忆必须绑定地点、物体、观测、位姿、时间、任务事件、置信度和来源证据 |
| 一个推理循环可以负责完整任务 | 慢速语义推理、waypoint推理和控制以不同频率运行，且必须明确各自控制权 |
| 工具输出可以持续追加到同一个对话 | 局部执行需要隔离上下文，只向全局规划器返回压缩结果 |
| 模型输出STOP代表任务完成 | 局部策略STOP只是证据，只有独立的终局验证器可以结束全局任务 |
| 动作是符号化且可撤销的 | 运动存在碰撞、惯性、控制误差、旧命令和人员安全风险 |
| 重试就是再次调用相同工具 | 恢复必须区分无进展、碰撞、定位失败、观测过期、目标不可达和语义歧义 |
| 一个目标字符串足以作为工具参数 | 导航需要落地的目标协议，包括语义目标、坐标系、空间锚点、约束和可观测完成条件 |
| 编排主要解决工具调用顺序 | 导航还必须同步观测、推理、规划、执行和验证 |

## 3. 必须实现的设计清单

### A. 控制权与运行状态

- [ ] 在 LLM 外部保留唯一权威状态机：`IDLE -> OBSERVE -> PLAN -> START_SKILL -> EXECUTE_SKILL -> VERIFY_SKILL -> VERIFY_FINISH`。
- [ ] 为每个任务、计划、技能执行、观测、模型请求和控制命令分配单调递增ID，拒绝任务或计划版本已经过期的结果。
- [ ] 分离全局任务、当前子目标、当前导航指令和控制器命令，不能让它们共用一个可变的 `instruction` 字段。
- [ ] 禁止 Hermes 或主 LLM 直接发布速度。它可以选择技能和定义完成条件，但运动必须由导航技能和本体适配器负责。
- [ ] 明确定义暂停、取消、抢占、超时和急停语义。暂停速度发送时不能隐式清空模型推理状态。
- [ ] 将局部 `STOP`、`WAIT`、`ARRIVE`、碰撞、超时和全局 `DONE` 定义成不同事件。

### B. 观测协议

- [ ] 使用强类型 `ObservationPacket`，包含传感器采集时间、接收时间、pose时间、相机名称、内参、外参、坐标系、有效性和序列号。
- [ ] 显式保留相机身份和顺序，绝不能只根据数组下标推断 `left/front/right`。
- [ ] 在 AgentOS Context Management 中实现任务自适应观测协议，支持视觉token预算、时间衰减、各相机权重和帧采样模式。
- [ ] 允许规划器根据任务选择观测策略：指令跟随使用更长历史，目标跟踪强调近期高分辨率帧，寻物可在探索与局部接近策略间切换。
- [ ] 保存每次模型输出实际使用的观测快照ID，保证视觉推理与动作结果可以追溯。
- [ ] 图像与pose需要时间对齐；如果无法插值，必须记录时间偏差，并允许新鲜度策略拒绝不安全观测。
- [ ] 确定性记录推理预处理过程，包括缩放、裁剪、压缩、旋转、颜色通道顺序和相机标签。

### C. 空间落地的子目标协议

- [ ] 规划器与导航技能之间不能只传自由文本，应使用包含任务模式、语义目标、空间锚点、约束和完成证据的 `NavigationIntent`。
- [ ] 支持多种锚点类型：文本地标、图像像素点、本体坐标点、世界坐标点、路径走廊、被跟踪实体和探索frontier。
- [ ] 每个空间锚点必须包含 `anchor_frame`、`anchor_timestamp`、`anchor_source`、`confidence`、`valid_until` 和 `observation_id`。
- [ ] 世界坐标锚点必须在每个控制周期重新投影到当前本体或相机坐标系，机器人运动后不能继续复用旧的本体系目标点。
- [ ] 当度量空间落地不可靠时，空间锚点可退化为带来源观测的像素目标，再由独立导航技能转换成waypoint；这是 CEE-AgentOS 的实现选择。
- [ ] 几何目标必须同时保留语义约束，例如“只走人行区域”“从门口进入”或“靠近但不能碰撞”。

### D. 慢快脑调度

- [ ] 慢速推理和快速导航异步运行。新的慢脑结果返回前，快脑可以执行最新且仍然有效的引导。
- [ ] 为每个慢脑引导结果添加版本号，只有更新且通过校验的结果才能原子替换当前缓存目标。
- [ ] 禁止无限堆积慢脑请求。最多允许一个正在执行的请求和一个可以被更新覆盖的最新请求，避免过期判断连续返回。
- [ ] 明确定义重规划触发条件：子目标完成、语义矛盾、目标丢失、持续无进展、碰撞循环、偏离路线或人工请求。
- [ ] 慢脑每次更新时不要自动清空导航历史，只有语义目标或任务模式发生实质变化时才重置。
- [ ] 控制器执行频率必须独立于云端推理频率。引导缺失或过期时应安全等待，而不是继续执行旧轨迹。

### E. 导航技能边界

- [ ] 每次导航技能在隔离的局部上下文中执行，其中只保存子目标、近期观测、局部轨迹、尝试次数、失败和恢复状态。
- [x] OmniNav Skill 返回压缩后的 `SkillResult`，不把原始图像、完整响应和prompt塞回主Agent上下文。
- [x] OmniNav 接口统一输出轨迹点、`[forward,left]` 坐标系、到达证据、时延和模型元数据。
- [ ] 将模型轨迹生成和轨迹跟踪严格分开。可替换的导航模型负责预测waypoint，pure pursuit、MPC或离散控制器负责执行。
- [x] 只有本体适配器可以把标准轨迹结果转换成Habitat动作；ROS2速度边界仍待实现。
- [ ] 同时记录实际odom和已经下发的命令，不能只记录模型预测轨迹。

### F. 验证与恢复

- [ ] 实现 ABot-AgentOS 风格的三级验证：运行时进展验证、技能完成验证和全局终局验证。
- [ ] 运行时验证必须检测位移停滞、重复碰撞、来回振荡、局部循环、观测过期以及命令与结果不一致。
- [ ] 技能验证必须用当前证据检查语义或空间子目标；RPC正常返回或OmniNav输出STOP均不能直接代表成功。
- [ ] 终局验证必须重新检查原始指令、所有完成条件、当前观测、轨迹摘要和仍未解决的子目标。
- [ ] 执行失败必须返回客观结果：实际移动情况、观察到的内容、停止进展的原因以及仍然缺少的证据。
- [ ] 恢复动作必须类型化：重新观测、旋转检查、重新定位、选择新锚点、重规划路线、重试控制器、请求云端推理或询问用户。

### G. 导航记忆

- [ ] 分离prompt上下文、episode工作记忆和跨会话持久记忆。
- [ ] 工作记忆应保持紧凑，只包含当前计划、已完成子目标、未解决证据、近期轨迹摘要、当前位置假设和最近目标观测。
- [ ] 持久记忆应保存有来源依据的结构化记录，而不是完整对话转储：实体、地点、事件、观测、会话、轨迹和来源节点，以及时空关系边。
- [ ] 视觉证据必须绑定图像帧ID和pose。例如“厨房在走廊左侧”必须保留产生该判断的来源和坐标上下文。
- [ ] 记录负面证据和被新信息替代的事实，例如“在pose P没有看到目标”或“门在时间T处于关闭状态”。
- [ ] 将机器人私有记忆和可共享的群体记忆分区，并根据隐私和置信度控制上传。
- [ ] 规划时只检索小型证据子图，不能把完整导航历史全部注入LLM上下文。

### H. 安全与端云协同

- [ ] 碰撞检测、控制看门狗、速度限制、人工接管和旧命令拒绝必须保留在端侧。
- [ ] 常规感知和状态跟踪优先在端侧处理，语义歧义、长程规划和失败诊断再升级到云端。
- [ ] 执行决策必须考虑网络数据年龄。模型推理速度快并不代表旧观测是安全的。
- [ ] 控制命令必须带租约或过期时间，租约到期后机器人必须停止发布运动命令。
- [ ] 云端不可用时可以维持最近的安全局部行为，但端侧不能在没有授权的情况下自行创造新的语义目标。

### I. 可追踪性与评测

- [ ] 使用同一个关联trace覆盖取帧、编码、上传、排队、模型推理、响应、控制器执行、odom变化和验证。
- [ ] 分开统计网络传输时间和模型推理时间，并额外统计从观测采集到命令生成的完整数据年龄。
- [ ] 保存模型实际输入的图像顺序、prompt、空间锚点、预测轨迹、控制命令历史、验证决定和任务终止来源。
- [ ] 参考 ABot-AgentOS，将完整任务成功率和目标条件完成率分开统计。
- [ ] 增加导航指标：SPL或路径效率、碰撞率、卡死率、重规划次数、过期结果拒绝次数、子目标成功率、错误STOP、遗漏STOP和人工接管次数。
- [ ] 按空间落地、感知、规划、控制器、定位、数据过期和验证进行失败分类，不能只保留一个笼统的失败标签。

## 4. 建议的 CEE-AgentOS 协议

| 协议 | 最少字段 |
| --- | --- |
| `ObservationPacket` | `observation_id`、采集和pose时间戳、具名相机帧、pose、坐标系、标定引用、新鲜度 |
| `ObservationPolicy` | 任务模式、token预算、时间衰减、相机权重、采样模式、历史时域 |
| `NavigationIntent` | 语义目标、任务模式、约束、完成条件、优先级、来源计划版本 |
| `SpatialAnchor` | 锚点类型、数值、坐标系、来源观测、置信度、过期时间 |
| `NavigationSkillRequest` | 导航意图、空间锚点、观测策略、控制器策略、超时、取消令牌 |
| `NavigationSkillResult` | 状态、局部STOP或ARRIVE、预测轨迹、实际轨迹摘要、新发现、失败类型、证据ID |
| `ExecutionReport` | 已下发命令、odom变化、碰撞或卡死信号、观测年龄、控制器状态 |
| `VerificationDecision` | 运行时/技能/终局阶段、判定、证据ID、缺失条件、建议恢复动作 |
| `MemoryEvidence` | 类型化实体/地点/事件、时空关系、来源ID、置信度、来源信息 |

## 5. CEE-AgentOS 的 AgentOS 分层

| 层级 | 建议负责人 |
| --- | --- |
| Hermes Core | 负责会话、模型provider、工具循环、插件加载、上下文压缩和通用trace |
| AgentOS Planner 扩展 | 以 Hermes planner/tool loop 为入口，生成任务图、技能依赖、完成条件和恢复策略 |
| AgentOS Skill Runner 扩展 | 维护任务版本、隔离执行上下文、技能生命周期、取消、抢占、超时和旧结果拒绝 |
| AgentOS 技能注册与路由扩展 | 通过 Hermes 插件注册能力，并按时延、算力、环境和置信度选择具体技能 |
| AgentOS Verifier 扩展 | 分别验证执行进展、技能完成和全局任务完成；语义不确定时才调用模型 |
| AgentOS Context/Memory 扩展 | 保存带来源的观测、地点、实体、事件、轨迹与验证结论，并向 Hermes 提供紧凑上下文 |
| 导航语义落地技能 | 初期使用 Qwen 35B，将开放任务转换成结构化语义目标和空间锚点 |
| 导航 waypoint 技能 | 当前使用 OmniNav，通过统一协议返回局部轨迹和模型证据 |
| 本体执行与安全 | Habitat 或机器狗端适配器负责轨迹跟踪、碰撞保护、看门狗和人工接管 |

Hermes 是 AgentOS 的依托框架，但不是物理执行状态的权威来源。CEE-AgentOS
通过 Hermes 扩展维护任务ID、技能状态、安全、验证和证据；本体运行时维护真实
运动状态。三者分层，不再存在第二套通用 Agent 主循环。

## 6. 实施优先级

### P0：先建立最小 AgentOS 闭环

- [ ] 实现权威任务状态机，以及任务、计划和技能执行的生命周期。
- [ ] 实现技能注册、能力描述、调用、取消、超时和结构化结果协议。
- [ ] 实现运行时、技能和全局终局三级验证，分离局部 `STOP` 与全局 `DONE`。
- [ ] 建立单调递增的任务、计划、观测版本和过期结果拒绝机制。
- [ ] 打通一个最小闭环：用户任务 -> AgentOS 规划 -> OmniNav 技能 -> 本体执行 -> 结果验证 -> 任务结束或恢复。
- [ ] 建立端侧命令看门狗、运动租约和人工接管。

### P1：补齐导航专用能力
